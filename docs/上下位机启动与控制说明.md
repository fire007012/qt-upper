更新：2026-11-21。**默认上位机和下位机运行在同一台主机。** 两台主机的连接方式仅见最后一节。

最近一次清理后的软件联动测试已通过，范围与证据见 [独立部署清理与联动验证](独立部署清理与联动验证.md)。

机械臂软件修复已发布，正式版本为 `robot24-field-arm-dualcan-20261120-2`。Qt 联动、MoveIt、Servo 和依赖检查通过；机械臂已按现有配置登记基线，真实电机运行需两路 CAN 在线，见 [机械臂专项检查](机械臂控制专项检查.md)。

## CAN 接入说明（实机使用前）

统一接口为 **can_driver 私有 CAN=can0、CANopen=can1**。底盘使用 can0，摆臂使用 can1；机械臂（含夹爪）需要两路都在线。当前两路均为 1 Mbps，须核对实际 USB CAN 卡对应的接口，不能只按插入顺序判断。

CAN 卡重新插入后，按实际使用的接口配置：

```bash
# can0：底盘、机械臂私有 CAN
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 txqueuelen 1000
sudo ip link set can0 up
ip -details link show can0

# can1：摆臂、机械臂 CANopen
sudo ip link set can1 type can bitrate 1000000
sudo ip link set can1 txqueuelen 1000
sudo ip link set can1 up
ip -details link show can1
```

接口已 UP 而需要改参数时，先将对应接口 down。已安装 CAN 插卡自动配置的下位机无需重复手动设置；不接电机的模拟场景可跳过本节。

### 单独启动摆臂后故障/通信超时

软件 ready、控制 TCP 就绪与电机运行许可是三种不同状态。只选摆臂时，上位机传递 `presets=["flippers"]`，正常按 `init → enable → resume` 执行，并在每一步完成后等待新鲜状态读回；初始化失败不会继续使能、运行或自动恢复。摆臂键盘输入使用**车体模式**，映射见[键盘说明](手柄键盘控制说明.md)。

启动页现在直接显示每组 `diagnostics.<group>.reason`，所选组 Fault 时摘要显示下位机原因及恢复入口；状态过期后清除这些实时提示。`heartbeat timeout`、`PDO feedback stale`、`stable feedback timeout`、`communication boot failed` 属于下位机 CANopen 初始化或反馈诊断，不能用放宽上位机 TCP 超时解决。`capability_discovery=timeout` 则是上位机未完成桥接能力发现，需要检查控制桥与 TCP 链路。

2026-11-21 用户确认“仅摆臂”故障发生在**另一台下位机**，未保留完整日志。本机已有上位机运行记录截至 11 月 17 日，包含底盘私有 CAN 反馈超时，没有这次摆臂故障证据，不能将其认定为同一根因。本轮完成上位机分步启动预算、显示修复和独立回归，摆臂实机超时尚未确认修复。

经用户授权，只读对照了 `~/ros2_ws_car` 的实际下位机源码和本机 `robot24-portable` 部署：选组裁剪会只保留摆臂四轴及 `groups_flippers` 总线资产；部署 hardware 档案将 flippers 映射到 can1；初始化为逐轴通信启动及稳定反馈等待，再经 enable 的 prepare/acknowledge/arm，最后 resume。这些路径未发现上位机跳步证据。实际下位机 `control_v2.py` 还包含“诊断可读才视为 runtime_fresh”的更新，不能用仓库参考副本代替目标机部署版本。

实际源码中 `RobotSystem::initializeGroup` 会在每轴通信启动成功后等待最多 3 秒的稳定反馈；PDO 默认 warn/stop/stable 为 50/100/100 ms，生成总线周期为 5 ms。这些是代码配置值，不证明目标机收到了相应帧。`verification/20261120-merged/hardware-smoke.json` 只验证软件启动及停止，四组保持 Stopped，没有初始化/使能电机。本机当前也没有 can0/can1；该事实不用于解释另一台下位机的故障。下一步须读取故障目标机的实际部署版本、接口状态及同一时段日志。

### 三目录对照发现的启动时间预算问题

已复现并修复的上位机问题位于 `src/communication/ControlSession.cpp`：原来整个选组、init、enable、resume 流程共用启动时设定的 60 秒截止时间。独立协议测试将三项操作分别延迟 25 秒、同时保持 token、心跳和状态正常，原实现会在 resume 尚未完成时标记 `LOCAL_OPERATION_TIMEOUT/result_unknown`。现仅在“操作成功且新鲜状态读回符合预期”之后，为下一阶段重新提供 60 秒预算；普通轮询、心跳和 accepted/running 回执不会续期。单阶段卡住仍超时、撤权，不重发、不自动恢复。

下位机与部署端仍有需协调的预算风险，已在 `~/ros2_ws_car` 与 `~/robot24-portable/install` 对应脚本中确认一致，未修改这些目录：

| 位置 | 实际行为 | 可能结果与下位机修改要求 |
| --- | --- | --- |
| `host_bridge/output_adapters.py` 的 `request/call_group_operation`；`robot_hardware_runtime/node.py` 的 `Adapter.call/prepare` | 桥接等整个 GroupOperation 默认 30 秒；内部 prepare 自身也可等待 30 秒，另有硬件状态切换、就绪等待、确认和清理 | 内层仍合法执行时外层先超时，桥接记录结果未知。应统一任务截止时间和剩余预算，外层包含内层收尾余量，或改为先返回任务 ID 后查询；不重放未知动作 |
| `RobotSystem::initializeGroup`；`NodeCanopenBaseDriver::add_to_master`；`Policy.verify` | 四轴顺序启动；每轴 boot 最多三次、单次 5 秒，随后稳定反馈最多 3 秒；按当前摆臂 bus 计算，基线核验还逐轴读取 38 项 SDO，共 152 项 | 一次或多轴启动缓慢时，完整初始化存在超出上述 30 秒的路径。需按整组预算设计初始化任务，超时后保留正在执行/取消/失败的真实状态及原始轴原因 |
| `GroupCoordinator._apply/_stop` 与桥接 `preset_status` | 失败后执行停止清理，组诊断可能变成通用停止原因；原始异常另存于 runtime `operations[group].reason`；桥接组状态只转发组 diagnostics | 原始 boot/SDO 超时可能被后续停止原因掩盖。接口应同时提供该组最后一次失败操作、阶段、轴、原始 reason；上位机不能从“已停止”推断根因 |

以上预算风险可以解释“软件可启动、运动初始化却超时”的部分路径，但没有远端故障日志，不能认定就是用户那次故障。应继续核对目标机安装版本、CAN1 实际接线及帧证据，而非统一增大心跳、PDO 安全期限。

下位机开发端需在独立授权工作区核查并交回以下证据；本仓库的 `ros2_ws_car/` 保持只读：

- 当前部署 hardware 档案中的摆臂组是否映射到实际 CANopen 接口（当前说明约定 can1），四轴 node ID、波特率及电源是否对应实物，预检是否只要求所选组设备。
- `RobotSystem::initializeGroup` 中各轴通信启动、NMT/heartbeat、`0x6041/0x6061/0x6064/0x606C` PDO 到达和稳定窗口；`prepareGroup` 中模式切换、使能与反馈确认。核对实际 PDO 周期是否满足每通道 warn/stop/stable 配置，不能靠屏蔽故障或无条件延长安全时限通过。
- `GroupCoordinator` 的 init/enable/resume 结果及任务 ID、故障发生时 `/robot_runtime/status` 的组/轴诊断、桥接 control_status、CAN 错误计数；确认慢初始化未阻断 owner heartbeat 或状态查询。未完成通信初始化的轴应报告未就绪，不能被当作已运行轴而提前触发运行故障。

处理设备或配置原因后，释放按键、归中，按界面要求允许操作并在“更多控制”中恢复所选组，再显式启动。保留上位机“连接设置”所示日志目录的 `runtime.jsonl` 与 `latest.json`，配合同一时段下位机 core/bridge 日志核对。未取得实机反馈与输出证据前，不标记实机验收完成。

## 开始前

下文约定两个工程位于当前用户的家目录（不再使用 `robot24-portable` 中间部署层）：

```text
~/hostcomputer/                 上位机
~/ros2_ws_car/                  下位机源码、构建产物与终端启动入口
~/.local/share/robot24/         终端模式下的本地运行配置、令牌与状态（可通过 ROBOT24_RUNTIME_DIR 覆盖）
/etc/robot24/ + /opt/robot24/   目标机启用 systemd 一键自启后的系统安装位置
```

`~` 自动代表当前用户的家目录，不需要填写用户名。上位机 `scripts/run_linked.sh` 按 `HOSTCOMPUTER_MANAGEMENT_CONFIG` → `/etc/robot24/manager.json` → `~/.local/share/robot24/manager.json` 自动查找配置。下位机终端启动 `bash ~/ros2_ws_car/src/tools/run_manager.sh` 时会自动初始化运行配置并带退避自恢复；目标下位机可通过 `bash ~/ros2_ws_car/src/tools/install_autostart.sh plan` 预览或 `sudo bash ~/ros2_ws_car/src/tools/install_autostart.sh install` 一键安装系统自启。

启动脚本优先使用 `~/hostcomputer/build/hostcomputer`，不存在时自动回退到 `~/hostcomputer/build-linked/hostcomputer`；可用 `HOSTCOMPUTER_BINARY` 指定其他程序路径。

每次只保留一个管理服务和一个上位机窗口。若管理服务已经运行，直接打开上位机，不重复执行管理启动命令。切换场景前先按第五节停止系统。

## 一、不接任何电机：同机模拟

**终端 1：启动下位机管理服务，保持终端打开。**

```bash
cd ~/ros2_ws_car/src
bash tools/run_manager.sh
```

**终端 2：启动上位机。**

```bash
cd ~/hostcomputer
bash scripts/run_linked.sh
```

**界面操作顺序：**

1. 打开“一键启动”，先在“准备启动的环境”选择 **`mock / 模拟`**，再点击“连接”；地址为 `127.0.0.1`，管理端口默认 `9091`，令牌自动预填。
2. 运动组全选，在“连接设置”点击“检查连接与环境”；部署档案只匹配所选的模拟环境。
3. 检查通过后，释放按键、手柄归中，点击“一键启动”。
4. 等待组启动完成、运行许可有效；顶部选择“键盘”，点击“返回键盘控制”，需要时点击“允许遥控”。

此场景只运行模拟软件，不驱动真实电机。

## 二、只接一个控制组：同机实机

**前提：** 下位机已部署 `hardware / 实机` 档案，该组设备、接口和参数已核验，并已完成开头的 CAN 接入配置。选择底盘时只勾选底盘。

**终端 1：启动下位机管理服务。**

```bash
cd ~/ros2_ws_car/src
bash tools/run_manager.sh
```

肩部 Node-ID 6/5 已按当前配置正式登记，hardware 使用 `commissioning-arm-registered.yaml`，无需先补采身份快照；机械臂基线预检已通过。两路 CAN 接好并配置后，选择机械臂组启动，先在轨迹模式的动作面板“刷新位姿”选择 `ready`，授权并点击“运动到该位置”；成功、输入归中后切换机械臂模式并重新允许遥控。

**终端 2：启动上位机。**

```bash
cd ~/hostcomputer
bash scripts/run_linked.sh
```

**界面操作顺序：**

1. 先在“准备启动的环境”选择 **`hardware / 实机`**，再点击“连接”，仍使用 `127.0.0.1`、管理端口和自动预填的令牌。
2. 只勾选实际接入的那个组，在“连接设置”点击“检查连接与环境”；部署档案只匹配所选的实机环境。
3. 预检通过、输入归中后，点击“一键启动”；等待所选组初始化、使能和运行完成。
4. 确认许可有效，选择键盘或手柄并允许遥控，再进行小幅控制。

**若提示服务未提供实机档案，此场景暂不能执行。** 界面会保留实机选择并禁止启动，不自动改成模拟。 需要先由下位机部署端补齐实机档案及设备映射；连接到本机不等于使用模拟，选择 mock 也不会驱动已接入的真实电机。当前独立部署包含 mock 和 hardware，实际可用档案与 revision 以管理服务查询结果为准。具体部署缺口见 [底盘实机部署要求](下位机设备参数维护接口要求.md)。

## 三、接入全车：同机实机

**前提：** 全车设备、CAN 接口、实机档案和参数基线均已核验。

**终端 1：启动下位机管理服务。**

```bash
cd ~/ros2_ws_car/src
bash tools/run_manager.sh
```

**终端 2：启动上位机。**

```bash
cd ~/hostcomputer
bash scripts/run_linked.sh
```

**界面操作顺序：**

1. 在启动页先选择 **`hardware / 实机`**，再点击“连接”。
2. 选择“全车组”，或全选摆臂、底盘、机械臂，点击“检查连接与环境”。
3. 预检通过、输入归中后“一键启动”，等待各组运行状态和许可确认，再允许遥控。

任何组未准备好或启动失败时，查看失败原因，不把软件已连接当成全车已允许运动。

## 四、查看同机连接参数（需要时使用）

管理服务启动后，另开终端：

```bash
cd ~/hostcomputer
python3 -B scripts/show_manager_connection.py --local
```

脚本显示本机连接地址、管理端口、认证令牌和监听状态。只读，不修改配置；分享输出时加 `--hide-token`。管理端口默认 `9091`，控制桥默认 `9090`，连接设置填写管理端口。

配置中的相对 `token_file`（例如 `manager.token`）按 `manager.json` 所在目录解析，不受终端当前目录影响。通过 `bash scripts/run_linked.sh` 启动上位机才会加载此配置并预填令牌；直接运行程序不会自动加载。若令牌为空，先用上述查询命令确认配置和令牌可读，再关闭旧上位机窗口、用脚本重新打开。

## 五、控制、停止和急停恢复

- **键盘：** 顶部“输入方式”选键盘，点击“聚焦键盘”；底盘 W/S 前后、A/D 转向，空格急停，侧栏显示“输入方式：键盘”、接收状态和当前按键，键盘模式不显示手柄连接按钮。
- **手柄：** “输入方式”选手柄，再连接手柄。切换输入、编辑参数或失焦后需归中并重新授权。
- **正常停止：** 松开输入 → “停止所选组”（全车时停止全部已确认组）→ “停止系统”并等待完成 → 关闭上位机。需要退出管理服务时，最后回终端 1 按 `Ctrl+C`。
- **切换模拟/实机：** 先选择目标环境 → “停止系统”并等待完成 → 检查环境 → “一键启动”。目标与当前运行环境不符时，界面分别显示二者，不自动接入另一种环境的控制端点。
- **急停恢复：** 处理原因并归中 → “处理急停” → “解除急停锁存” → “允许恢复操作” → “复位全局禁止” → 重新启动所选组。按钮禁用时查提示，不删除持久状态绕过锁存。

小屏或高缩放下可使用面板和工作区的滚动条。详细输入和诊断见 [手柄键盘说明](手柄键盘控制说明.md)、[控制与诊断](Qt控制v2与诊断使用.md)。

## 六、上位机和下位机不在同一台主机

**下位机终端 1：启动管理服务。**

```bash
cd ~/ros2_ws_car/src
bash tools/run_manager.sh
```

**下位机终端 2：查询地址、端口和令牌。**（此处不加 `--local`。）

```bash
cd ~/hostcomputer
python3 -B scripts/show_manager_connection.py
```

下位机若没有上位机工程，只需复制 `show_manager_connection.py` 一个文件；在脚本所在目录运行（默认自动查找 `/etc/robot24/manager.json` 或 `~/.local/share/robot24/manager.json`），或用 `--config` 显式指定配置。

**上位机终端：** 把 `下位机IP` 换成上一步与本机网络互通的网卡地址。

```bash
cd ~/hostcomputer
bash scripts/run_linked.sh --vehicle 下位机IP
```

在启动页先选择 mock/hardware，在“连接设置”填写查询到的管理端口和令牌，再点击“连接”；之后按前面对应场景选择运动组并检查环境。`--vehicle` 只选择远端地址，不切换实机模式。

跨主机部署还须将下位机 `runtime/manager.json` 中 `control_endpoint.host` 设置为上位机可达的下位机实际 IP，并确认管理服务和控制桥允许非回环监听、网络及防火墙可达；修改后重启管理服务。连接框不能填 `0.0.0.0`。跨主机使用实际 IP，同机继续使用 `127.0.0.1`。`ROS_LOCALHOST_ONLY=1` 可保留，内部 ROS2 仍在下位机运行，不影响 TCP 远程连接。`--vehicle` 只设置管理服务地址，不会替你修改控制桥公布地址。
