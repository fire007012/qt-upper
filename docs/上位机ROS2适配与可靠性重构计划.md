- 旧根目录 `ros1_bridge/` 已整体移至 `archive/ros1/ros1_bridge/`，仅作退役历史参考，不再参加当前构建、测试或部署；现场运行版本仍须按实际部署登记。

- ROS2 工程已有 `robot_bringup`、`robot_hardware`、`robot_safety`，包含 mock/实机启动、分组运行及维护逻辑，应复用现有能力。

- 本文包含跨上下位机的整体设计；涉及 ROS2 桥接修复、管理服务、systemd、下位机配置及启动入口的工作均属于下位机协作任务，不是上位机开发端的代码修改授权。上位机端负责 Qt、客户端协议适配、独立 mock、文档与联调；接口尚未实现时明确记录依赖，不修改参考目录补齐。

### 2.2 P0 原始基线证据与待验证假设

本表保留重构前的定位依据，其中Qt重连、ACK、单调计时和控制v2已按实施记录修复，不能把表内历史代码行为当成当前实现。现场唯一根因仍需实际故障证据确认。

| 位置 | 已看到的事实 | 需要验证的影响 |
| --- | --- | --- |
| `archive/ros1/ros1_bridge/bridge_core.py::handle_operator_input` | 使用桥接 `now_ms()` 与上位机 `timestamp_ms + ttl_ms` 比较，默认输入 TTL 在 Qt 中为 300ms | 两机时钟偏差或校时可能导致持续 `dropped_expired`；但还不能证明这是现场唯一根因 |
| `src/communication/RobotTcpClient.cpp::checkConnection` | 心跳 ACK 超时后只设置离线标记，没有在该分支主动关闭半开连接 | socket 显示连接成功，但业务已经失效时可能无法自动恢复 |
| `RobotTcpClient.h` 与重连逻辑 | 心跳周期 1s，重连间隔 3s，最多 5 次 | 长时间掉网后可能停止恢复；首次连接失败路径也要单独验证 |
| `RobotTcpClient.cpp::handleHeartbeatAck` | 未匹配到待处理序号的 ACK 也会更新在线状态 | 迟到或无关 ACK 可能造成错误在线判定 |
| 两份桥接的 `BridgeClient.run` / `BridgeCore` | 支持多个 TCP 客户端，但使用共享输入序号；新连接会重置共享输入状态 | 第二个客户端、重连旧线程或调试工具可能干扰控制会话 |
| ROS2 `bridge_core.py` | 已计算时钟偏差和输入年龄，但当前 `handle_operator_input` 没有根据 TTL 拒收；watchdog 仍使用墙上时钟差 | 不能将 ROS2 版本直接当成完整修复，需补齐积压旧输入防护和单调计时 |
| ROS2 `output_adapters.py::state` | 根据运行状态中的 `groups`、`operations` 内容变化触发输入会话重置 | 需核对变化频率及真正的运行 epoch，避免普通状态更新反复清空输入状态 |

重点区分四类故障：TCP 断开、TCP 半开/心跳失效、输入被拒收、ROS2 运行端未就绪。重启能恢复说明进程内状态值得检查，不能单凭这一现象认定为心跳故障。

## 3. 目标架构

```text
Qt 上位机（无 ROS 依赖）
  操作页 / 运行管理页 / 配置维护页 / 诊断页
                 │
  应用服务：控制、连接会话、运行管理、配置管理、状态仓库
                 │ TCP/JSON：协议版本、会话、输入、请求/结果、状态
                 ▼
ROS2 host_bridge
  连接与控制权 / 命令新鲜度 / watchdog / 协议与诊断
                 │
  控制适配 ── ROS2 topics/services/actions ── 现有控制与安全运行端

Qt 上位机 ── 独立管理连接 ── 下位机管理服务（开机自启）
                              配置档案、进程管理、持久化与回滚
                              启动 ROS2 / host_bridge / 所选视频模块

视频：保留现有 RTSP + MediaMTX/视频管理链路，独立管理故障状态。
```

管理服务是 P1 新增能力，必须开机自启，且在 ROS2、`host_bridge` 和视频进程均未启动时可访问。Qt 直接连接该服务，不能通过尚未启动的桥接间接发起启动。管理服务及连接独立于运动控制链路，具体协议和端口在接口设计时固定。

Qt 不通过拼接 SSH 命令直接修改文件或执行任意 shell。节点依赖、启动顺序和硬件约束集中在下位机管理层；ROS2 运行与安全层继续作为允许运动的最终依据。

## 4. P0：失联治理与 ROS2 对接

### 4.1 先建立可复现基线

1. 登记现场 Qt、桥接、ROS2 工作区版本、启动命令、有效配置、主机时间及网络拓扑；记录桥接实际运行位置，不凭目录名称推断部署位置。
2. 持久记录连接 ID、会话 ID、输入序号、最近接收/接受/输出时间、心跳 RTT、拒收原因、运行状态、队列深度和服务耗时。
3. 在无运动输出的 mock/dry-run 环境复现：上下位机分别重启、掉网、只丢 ACK、两机时钟偏移/跳变、第二个客户端连接、慢服务、视频异常及输入积压。
4. 保存故障前后日志和必要的报文证据，明确重启桥接究竟清除了哪个异常状态。

交付：故障复现脚本、根因记录和针对根因的回归用例。现场暂不能复现时，先发布诊断构建并完成已知缺陷修复，结论标记为待现场验证。

### 4.2 明确连接与会话状态机

- Qt 使用 `Disconnected → Connecting → Negotiating → Syncing → Ready`，异常进入 `Degraded/Reconnecting`；主动断开则停止自动重连。
- TCP 连接、匹配心跳、协议协商、状态同步和下位机就绪分别表示，不再用一个“在线”灯代表全部状态。
- 协商响应、首次心跳和后续心跳都有本地单调时限；无有效响应时关闭旧 socket，再按带抖动、有上限间隔的退避策略持续重试。
- 每次连接创建新会话；序号、ACK、时钟估计、解析残留及按键边沿属于该会话。旧连接回调不能修改新会话。
- 建立单控制端租约；监控客户端只读，不能重置控制输入状态。控制权转移先撤销旧租约并归零。
- 会话标识由桥接签发并绑定连接；明确控制会话与下位机运行 epoch 的关系，只有真实会话失效才撤销控制权。

### 4.3 分离心跳、输入有效期与运行许可

| 机制 | 负责判断 | 约束 |
| --- | --- | --- |
| 心跳 | 应用通信是否双向可用 | 只接受本会话且匹配待处理序号的 ACK；心跳不能刷新运动输入 watchdog |
| 输入序号 | 是否重复、倒序或属于旧会话 | 在本控制会话内递增；拒收时返回明确原因 |
| 输入新鲜度 | 命令是否因传输/排队而过时 | 不依赖两机墙上时钟相等，也不能仅以“刚收到”认定新鲜 |
| 输入 watchdog | 多久没有接受新的有效输入 | 使用接收端单调时钟；超时撤销运动输出；拒收输入不刷新计时 |
| 运行许可 | 当前组、急停和控制器是否允许运动 | 以 ROS2 安全及运行状态为准；通信恢复不隐式恢复运动 |

建议的新鲜度方案：桥接周期签发短期 freshness token，保存其本地单调签发时间；Qt 发送输入时回带 token，桥接验证 token 属于当前会话且未超过约定窗口。token 生命周期、更新频率和输入 TTL 一并协商，过期后必须等待新 token 并重新采样输入。这样可限制旧 TCP 队列中的输入，不依赖发送端系统时间。第一阶段通过延迟/积压测试确认该方案的时序预算后固定协议。

墙上时间仅用于日志追踪；Qt 超时和 RTT 使用 `QElapsedTimer` 等单调时钟，Python 使用 `time.monotonic()`。保留 `timestamp_ms` 便于诊断，但不以跨机器墙上时间差直接决定控制许可。

只保留待发送的最新连续输入快照，设置发送缓冲上限；超限使会话降级并清除积压。离散操作和连续输入分开处理，已过期的离散操作不得重放。

失联、watchdog 或控制权丢失后输出归零；网络恢复后先同步状态、清空旧按键与摇杆状态，并要求中立输入和明确重新授权。急停状态跨 TCP 重连保留。下位机独立 watchdog 必须覆盖桥接崩溃或线程阻塞，不能只依赖桥接发出一次零命令。

### 4.4 避免服务调用阻塞通信

- 心跳、收发和 watchdog 不等待 ROS2 长耗时 service/action、视频 IPC 或配置操作。
- 对长任务采用有界任务队列，区分“请求已接受”“执行完成”“失败”“超时且结果未知”；必要时提供状态查询和取消。
- 关键操作使用 `request_id`、结果缓存与幂等规则。ACK 超时不盲目重复 init/enable/配置应用等有副作用操作。
- 明确 ACK 表示接收还是完成，Qt 等待时间与服务端执行时限一致；慢客户端不能阻塞全部广播。

### 4.5 ROS2 协议和业务适配

1. 建立接口矩阵：底盘、Servo、摆臂、夹爪、关节状态、CO₂/IMU、相机、命名位姿、急停、运行控制；逐项记录消息类型、单位、坐标系、服务/action 路径、失败语义和就绪条件。
2. 重点核对夹爪从位置到速度的变化、摆臂 profile、`/robot_runtime` 操作、分组状态与运行 epoch，避免只改 ROS API 名称。
3. 对接现有 ROS2 `host_bridge`，所需桥接修改交由下位机开发端在独立工作区实施；上位机端不得修改 `ros2_ws_car/`。下位机侧保持无 ROS 的协议/会话核心可独立测试；上位机测试 mock 位于参考目录之外，不依赖旧 ROS1 生产目录。
4. Qt 通信类已更名为 `RobotTcpClient`，构建和测试同步迁移；历史类名已退出生产代码，当前 Qt 仍只依赖 TCP/JSON。
5. 为新会话和 freshness 能力升级协议，握手同时核对版本与必需 capabilities。不兼容时给出升级信息并禁用运动控制，避免静默降级丢失安全约束。
6. 固定 Qt、桥接和下位机的兼容版本表及构建标识；旧 `sync_ros1_bridge.py` 已归档并禁止执行部署，不能向 ROS2 复制旧代码。

### 4.6 P0 验收门槛

以下为建议发布门槛；时间值在阶段 M0 按实际输入周期和网络预算确认。

| 场景 | 验收要求 |
| --- | --- |
| 两机墙上时间相差 ±24h，运行中分别前跳/后跳 | 有效输入持续可用；过期输入仍被拦截；watchdog 和 RTT 不受墙上时间变化影响 |
| 物理断网、桥接重启、Qt 重启、半开连接，各 100 轮 | 无需人工重启桥接恢复通信；网络恢复且服务就绪后目标 10s 内完成握手与同步；不恢复旧运动 |
| 首次连接失败、首次 ACK 缺失、连续 ACK 缺失、旧 ACK 到达 | 有界时间降级并重试；旧 ACK 不标记在线；主动断开后不继续重试 |
| 连续输入停止而心跳继续 | 在协商 watchdog 时限加已测调度容差内归零；同时验证下位机实际接收和输出状态 |
| 延迟、积压、旧会话重放及重复序号 | 拒收旧输入，不因积压命令再次运动；拒收原因可见 |
| 第二控制端、只读监控端、旧连接迟到回调 | 控制权唯一；监控不影响输入序号；旧会话不改变新会话 |
| ROS2 服务耗时 30s、视频不可达或慢客户端 | 心跳与 watchdog 仍按时运行，关键请求结果可追踪 |
| 下位机分组恢复及普通状态更新 | 真正的 epoch 变化使旧授权失效；普通遥测变化不反复重置控制会话 |
| 急停期间掉网再重连 | 急停保持，状态同步准确，恢复运动需要显式操作 |

软件验收先使用 mock/仿真；实机验收另行记录输出归零、控制器行为和恢复流程，不能以 TCP ACK 代替硬件验收。

## 5. P1：配置与运行管理

### 5.1 配置分层和唯一来源

| 配置类别 | 示例 | 保存和生效位置 |
| --- | --- | --- |
| 上位机偏好 | 地址、布局、输入映射 | Qt 本地，不包含下位机配置副本作为权威来源 |
| 机器人配置档案 | 机器人 ID、模块、网络、视频源、控制限值 | 下位机管理服务；Qt 查询、编辑、提交 |
| 硬件与标定 | 电机 ID、CAN 接口、方向、减速比、编码器、零位、单位、限位 | 下位机版本化配置；维护状态下应用 |
| 生成及部署产物 | ROS 参数、总线/DCF、控制器配置 | 从受控源配置生成；Qt 不直接编辑生成文件 |

每份档案包含 schema 版本、revision、内容摘要、修改记录及生效状态；服务端返回字段类型、单位、范围、依赖和是否需停机/重启。明确“已编辑、已保存、已部署、已生效、待重启”几个状态。

现有参数需要建立来源映射，覆盖 `bridge_control.yaml`、视频源配置、`robot_hardware/config`、`robot_canopen_config` 源配置与生成链。禁止一次性合并所有 YAML 后形成第二份难以维护的事实来源。

### 5.2 电机配置闭环

```text
读取有效配置和 revision
 → 编辑并校验 → 查看差异与影响范围 → 保存候选版本
 → 进入维护/停止受影响组 → 下位机再次校验运行前提
 → 生成及校验产物 → 备份并应用 → 必要的重启/重载
 → 读取实际生效值并检查 → 标记成功或回滚
```

- 先覆盖最常改动的字段，M0 收集现场修改清单；不承诺所有驱动参数都支持在线修改。
- 使用 revision 检测并发修改；连接断开后按操作 ID 查询结果，避免重复应用。
- 分清运行参数、启动参数、生成配置和设备非易失参数。写电机持久参数应为独立维护操作，不能随普通“保存”隐式执行。
- 多文件部署采用版本目录和受控切换；应用失败恢复上一可用版本。涉及物理设备写入时明确可逆范围，不能宣称文件回滚等于设备已回滚。
- 更改电机方向、比例、零位或限位后要求重新检查受影响轴；配置恢复不自动恢复运行授权。

### 5.3 统一启动与部署

- **日常入口固定为上位机“启动系统”按钮**：首次部署完成后，下位机通电并联网，用户打开 Qt，自动连接已保存的机器人档案，点击一次即可完成启动。上位机打开本身不自动触发运动或运行授权。
- 一键流程：连接管理服务 → 确认档案及配置版本 → 预检 → 按依赖启动所选模块 → 等待健康和就绪检查 → Qt 连接控制桥接并同步状态 → 显示“软件已就绪，待授权”。不得将进程存活或端口可连直接当成最终就绪。
- 下位机管理服务随系统开机启动，具有独立的状态查询和日志接口；ROS2 或桥接未运行、崩溃及被停止时，管理入口仍可用。
- 下位机管理服务复用 `robot_bringup` 的已有 launch，提供 mock/实机及模块 profile；UI 不暴露零散 launch 参数作为日常操作入口。
- 预检包括配置版本、构建版本、端口、CAN 设备映射、所需依赖、视频源和模块健康；返回可操作的失败原因。
- 启动流程提供阶段进度、日志、幂等启动、停止和失败后的清理；按照现有运行状态区分“进程已启动、硬件已初始化、已使能、获准运行”。
- 保留 `init → enable → resume` 的明确语义，启动程序不自动放行运动；分组恢复复用下位机能力。
- 提供固定发布目录、配置目录和日志目录，发布包携带版本清单。Qt 沿用现有 Qt/FFmpeg 打包要求，ROS2 桥接按安装产物部署。
- 从旧配置导入生成差异报告，缺失字段不自动填入未经确认的设备值；ROS2 继续作为活动基线。回退使用上一套验证过的匹配 ROS2 发布包，不规划自动回退 ROS1。

### 5.4 一键启动的接口和状态约定

- 提供管理握手/能力查询、档案查询、预检、启动、停止、状态快照、操作查询和分页/游标日志接口。传输协议、端口、认证及 schema 在 M3 开始时固定，上位机不内置下位机 shell 命令。
- 启动请求包含 `request_id`、`robot_id`、`profile_id` 和 `config_revision`，返回 `operation_id`。重复提交同一请求不得创建第二套进程；同一机器人并发启动应返回已有操作或明确冲突。
- 任务采用 `accepted/running/succeeded/failed/cancelled`，执行阶段独立记录为预检、模块启动、健康检查等；长任务不阻塞管理状态查询。
- 系统软件状态采用 `stopped/starting/ready/degraded/stopping/failed`；硬件初始化、使能、运行许可和急停独立返回。`ready` 不等于已允许运动。
- 进度包含当前阶段、各模块状态、错误码、失败原因、是否可重试、日志游标，以及配置/软件版本。明确 profile 的必需模块和可选模块，可选模块失败是否允许降级由档案定义。
- Qt 关闭或管理连接短暂断开不自动终止已接受的启动任务。Qt 重连后查询原任务并恢复显示，不重复启动；运动控制断连仍独立执行 P0 的归零与授权规则。
- 明确进程归属、整车 launch 与独立视频服务的依赖，避免双重拉起。失败清理只处理本次创建的资源；停止按依赖逆序执行并先确保运动停止，不停止管理服务自身。
- 管理服务重启后核对现有受管进程、配置版本和操作记录，不仅根据磁盘上的旧状态宣告就绪；通过服务管理器监管并提供持久操作记录。
- 管理接口限定可执行操作与配置目录，并提供部署认证机制；Qt 不持有 root 密码，日志不输出认证凭据。
- 下位机物理关机时的一键开机不属于本轮默认范围；若需 Wake-on-LAN 等能力，在确认硬件、供电及网络条件后单独扩展。首次安装管理服务和网络配置属于部署工作，完成后日常无需终端操作。

### 5.5 一键启动验收

| 场景 | 验收要求 |
| --- | --- |
| 下位机冷启动，仅管理服务自启 | 从 Qt 点击一次完成预检、所选模块启动和桥接状态同步，无 SSH、手动 source 或额外终端操作 |
| 重复点击、请求重发、第二个上位机同时启动 | 每套受管系统只有一份实例，返回原操作状态或明确冲突 |
| 启动中断开 Qt，再打开 | 原任务继续可查询，界面恢复当前进度，不重复拉起进程 |
| ROS2/桥接未启动或崩溃 | 管理服务仍可访问，能查询原因并执行受控重试 |
| 配置无效、设备缺失、端口占用、必需节点超时 | 返回对应阶段、结构化错误与日志，不能显示启动成功；清理本次创建的资源 |
| 可选视频模块异常 | 按档案显示降级及影响，不把视频故障误判为控制链路正常或失效 |
| 管理服务在任务中重启 | 对账实际进程与任务，状态可信，可继续查询和受控恢复 |
| 停止后再次启动，连续 20 轮 | 无重复进程、孤儿进程和端口残留，管理入口持续可用 |
| 软件就绪、掉线重连或任务重试 | 均不自动解除急停，不自动 enable/resume，不执行旧运动命令 |

下一轮下位机协作使用 [P0与配置事务增量提示词](下位机P0与配置事务增量协作提示词.md)；[初版一键启动需求](下位机一键启动协作提示词.md) 仅作留档，已交付管理v1不重复开发。

## 6. P1：Qt 上位机重构

### 6.1 界面职责

| 页面 | 核心内容 |
| --- | --- |
| 操作 | 现有视频、运动输入、急停、关键遥测；持续显示控制权、输入是否接受和运行许可 |
| 运行管理 | 机器人档案选择、一键启动/停止、阶段进度、断线后任务恢复、分组状态、初始化/使能/恢复、失败原因及重试 |
| 配置维护 | 电机参数表、字段单位和范围、版本差异、备份、应用、生效检查及回滚 |
| 诊断 | TCP/心跳/协议/输入/ROS2 状态、拒收计数、请求进度、日志及诊断包导出 |

P0 先在现有状态区补足诊断信息，P1 再调整整体布局。日常运行隐藏工程细节，维护页提供必要的参数来源和应用影响。

### 6.2 代码拆分

- `RobotTcpClient`：传输与分帧；`SessionManager`：握手、心跳、重连、控制租约；`ProtocolCodec`：协议编解码和校验。
- `ControlService`：输入采样、最新快照、模式和授权；`RuntimeService`：运行命令与任务状态；`ConfigurationService`：配置事务；`RobotStateStore`：统一的实际状态。
- 从 `mainwindow.cpp` 和 `Controller` 中逐步迁出协议分支与业务状态，UI 只绑定状态和发出操作意图，避免日志文字成为状态判断依据。
- 保留视频和输入模块，在接口稳定后逐页迁移。状态仓库在断开时明确标记数据过期，不能继续把旧遥测显示为实时值。

## 7. 实施顺序、交付与工作量

下表及总工期为上下位机协作范围：M1/M2 中的桥接与 ROS2 修改、M3 管理后端由下位机开发端负责；Qt、独立 mock 和客户端适配由上位机开发端负责。各端只在自己的获授权代码范围内修改，上位机工作区内的 `ros2_ws_car/` 始终只读。

| 阶段 | 交付内容 | 出口条件 | 粗估工作量 |
| --- | --- | --- | --- |
| M0：基线与契约 | 现场版本登记、复现、接口矩阵、常改配置清单、协议及计时预算 | 根因证据或待验证假设明确，P0 验收方案可执行 | 2–3 人日 |
| M1：P0 修复 | 单调时钟、会话/控制权、输入新鲜度、心跳强制恢复、关键诊断与回归 | 断网/时钟/积压/多客户端测试通过 | 5–8 人日 |
| M2：ROS2 联调和 P0 发布 | ROS2 接口适配、运行状态同步、兼容版本表和发布包 | mock/仿真及短时故障恢复回归通过，现场验证单独签收 | 4–6 人日 |
| M3：管理后端 | 开机自启管理服务、管理协议、幂等启动及任务恢复、配置事务、进度/日志与回滚 | 独立客户端通过 5.5 验收；无 Qt 时也能验证完整配置和运行闭环 | 8–13 人日 |
| M4：Qt 维护与运行界面 | 一键启动与进度恢复、服务拆分、运行/配置/诊断页面、常用参数编辑 | Qt 端完成 5.5 验收；工程维护无需直接改源码或多处 YAML | 7–11 人日 |
| M5：迁移与交付 | 配置导入、匹配发布包、部署说明、现场操作手册 | 从干净环境完成安装、启动、配置、回滚演练 | 3–5 人日 |

粗估合计 29–46 人日；P0 约 11–17 人日。已计入一键启动管理服务、任务恢复和 Qt 联调。估算假设 ROS2 栈现有接口可复用、人员熟悉工程，不包含硬件故障处理、现场排期和新增驱动开发；M0 后根据根因及电机参数覆盖范围更新。

P0 通过后先独立交付，再进入 P1。管理后端接口通过评审并具备可验证实现后再做完整 Qt 页面，减少界面返工。

## 9. 实施前仍需确认的事实

以下通过现场检查或 M0 联调确认，不阻塞本文评审：实际部署的桥接版本与运行机器；失联时是否存在 `dropped_expired`/`dropped_old_seq`；是否有第二控制客户端；常改电机参数及是否写设备持久存储；最终管理服务部署位置；实机验收窗口。

这些事实可能改变局部实现与工期，不改变“P0 先保证链路和输入有效性、ROS2 为活动基线、P1 由下位机统一执行配置与启动”的总体顺序。
