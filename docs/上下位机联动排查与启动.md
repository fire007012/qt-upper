# 上下位机联动排查与启动

检查日期：2026-11-14。上位机 `/home/fire/hostcomputer`，下位机 `/home/fire/ros2_ws_car`。本页保留首次排查发现和通用部署步骤。随后用户临时授权两边修改、完整构建及依赖安装；最新产物、启动入口与具体修改以 [联动交付记录](上下位机联动交付记录.md) 为准。首次验证产物在 `/tmp/host-link-*`。

## 联动路径

```text
Qt 运行管理页 → TCP 9091 / robot_manager（管理协议 v1，认证令牌）
                      ↓ 预检、启动 core 和唯一一份 bridge
Qt 控制客户端 → TCP 9090 / host_bridge（控制协议 v2，robot_id）
                      ↓ ROS2 运行协调器、底盘、Servo、摆臂、夹爪
Qt 视频播放器 ← TCP 8554 / RTSP 服务（地址由 camera_list 提供）
```

上位机通过 TCP 接入，不需要在上位机安装 ROS2 或把两台机器加入同一 DDS 域。控制桥与运动节点在下位机使用同一 ROS2 环境。管理服务负责软件进程，控制桥负责明确授权后的运行操作。

## 当前发现与修复

1. 完整 Qt6 应用可以编译，但本次实际复现了退出崩溃：`RtspPlayerWidget` 已进入基类析构后，子解码器析构再次发出 `stopped()`，触发派生类槽的 Qt 类型断言。现于播放器析构时断开解码器到播放器的回调，再停止解码器；新增视频窗口生命周期回归。
2. 当前 `/home/fire/ros2_ws_car/install` 的安装包只有 `can_driver`、`canopen_interfaces`、`robot_hardware`、`robot_safety`。本次 source 后，`robot_bringup`、`host_bridge`、`car_control`、`arm_control` 均无法通过 ament 查到。因此该 install 不能直接作为整车联动安装环境。源码存在不代表对应 ROS 包已安装。
3. 管理示例的 `bind`、`bridge_bind`、`control_endpoint.host` 均为 `127.0.0.1`。跨机器连接必须配置实际网络地址。
4. 默认地址并不统一：运行管理页为 `192.168.1.100`，手动控制连接为 `192.168.1.123`，下位机本地视频 YAML 的 `rtsp.public_host` 为 `192.168.1.83`。这些只是当前默认/配置值，不能据此判断真实机器人 IP；部署时应统一为下位机实际可访问地址。历史 QSettings 也会覆盖界面默认值。
5. 原只读契约夹具早于分组控制升级，只统计旧 lifecycle，并且临时 ROS 接口缺少 `GroupOperation`。已补充分组模拟服务、全局禁止模拟反馈，并等待在途输入 ACK，保留真实协议、未知结果及急停断言。

## 下位机准备

以下是下位机开发/部署端需执行的步骤，本次未修改其部署、启停系统服务或接入 CAN。

从源码根目录构建完整工作区，产物放到独立目录：

```bash
cd /home/fire/ros2_ws_car/src
bash tools/build_ros2.sh /tmp/robot24-link full
source /tmp/robot24-link-install/setup.bash
ros2 pkg prefix robot_bringup
ros2 pkg prefix host_bridge
ros2 pkg prefix car_control
ros2 pkg prefix arm_control
```

只有完整构建成功且这些包都解析到预期安装位置，才进入启动阶段。生产部署使用正式安装目录，并让 manager 配置的 `setup` 指向该目录；不要仍指向当前不完整的 `ros2_ws_car/install`。

先使用下位机已有的 `mock` 档案联调软件。真实 `hardware` 档案还须完成已有 commissioning、设备身份及现场验收要求，不能把示例基线视为已登记。

跨机器时，在正式 manager 配置中设置以下字段；将占位符替换成实际值，保留原有状态、令牌、档案及发布清单配置：

```json
{
  "robot_id": "robot24",
  "setup": "/实际完整安装目录/setup.bash",
  "bind": "0.0.0.0",
  "port": 9091,
  "bridge_bind": "0.0.0.0",
  "network_policy_confirmed": true,
  "control_endpoint": {
    "host": "下位机实际IP",
    "port": 9090,
    "protocol_version": 2
  }
}
```

`0.0.0.0` 仅用于服务监听，不能填作上位机连接地址。令牌长度至少 32，文件权限 0600，上位机填写同一令牌。档案 `build_version` 必须与 manager 和发布清单一致，档案 revision 使用服务实际返回值。部署网络按下位机 README 的可信网要求配置。

管理器预检会检查发布清单、包/设备依赖和端口占用。使用管理路径时不要提前手工启动第二份整车或桥接；管理器已有唯一进程归属逻辑。实际部署检查可运行：

```bash
python3 -B /home/fire/ros2_ws_car/src/robot_manager/deployment_check.py \
  --config /etc/robot24/manager.json
```

## 上位机操作顺序

1. 使用 Qt6 构建程序。本次可执行文件为 `/tmp/host-link-app/hostcomputer`；从桌面图形会话运行，检查版本应为 `host-ros2-v2-field-1 Qt 6.12.0`。
2. 在运行管理页填下位机实际 IP、9091 和令牌，连接后选择服务提供的档案与 revision，执行预检，再明确启动软件。
3. 软件 ready/degraded 后，上位机使用 manager 返回的控制端点连接 9090，核对 `robot_id=robot24` 和控制 v2 能力。管理协议仍为 v1，不要把管理连接也改成 v2。
4. 选择运动预设、释放按键并让手柄归中，按界面明确启动预设。流程为 `init → enable → resume`，每步等待实际状态；ready 只表示软件健康，不等于已允许运动。之后明确允许遥控。
5. 断线、epoch 改变、换档和急停后都需要重新同步、中立及明确授权。结果未知的操作查询原 ID，不重复点击创建新操作。急停解除按既有 `clear_emergency → reset_global_stop → 显式恢复` 流程执行。
6. 控制稳定后再接入视频。确认 `rtsp.public_host` 是上位机可访问的下位机地址，8554 服务存在，相机设备/源真实有效。管理视频由同一 video stack 持有桥接，避免重复启动桥接。视频异常应独立排查。

## 根据错误定位

| 现象/错误 | 处理 |
| --- | --- |
| `Package ... not found` | 完整构建并 source 正确安装目录，检查 manager.setup |
| 连接拒绝/超时 | 核对 IP、9091/9090 监听、bind 和网络可达性 |
| 管理认证失败 | 核对令牌；不把令牌写入日志或提交源码 |
| 预检端口占用 | 对账已有进程，避免管理器与手工启动重复拥有 bridge |
| `OWNER_BUSY` | 已有控制端占用会话；关闭旧控制端或用只读监控角色 |
| `EPOCH` | 同步新状态、归中并重新授权；查询在途操作 |
| `RUNTIME_NOT_SETTLED` / 反馈过期 | 核对下位机真实 runtime、组状态和诊断，不能绕过检查 |
| RTSP 播放错误 | 检查公布地址、8554、实际设备与编码；不是控制协议错误 |
| Quick3D 非 QRhi 提示 | 无显示环境的 offscreen 软件后端不能证明 3D 渲染；桌面会话另测 |
